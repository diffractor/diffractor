1.27.2 is a feature release with two subjects: a panorama viewing mode, and the first stage of the Linux port. They are independent — the first is `User-visible behavior`, the second is `Internal` until a Linux build exists — and each can ship without the other.

## Planned

### 1. Panorama display

**Owned by [zoom](zoom.md) and [design](design.md); the metadata it reads is owned by [metadata](metadata.md).**

An image carrying panorama metadata is not served by `Fit`: fitted to a browsing window a 12000x1000 stitch is a bright line. Zooming such an image should put the user inside it — 100% scale, the pointer looking around rather than dragging a scrollbar — instead of leaving them to pan a very wide rectangle by hand.

The intent, in the terms the [zoom model](zoom.md#2-the-model) already uses:

- Panorama display is **not a third magnified state**. Zoom's model is one scale and one source-space center, and a panorama is that model with the scale pinned to 100% and the center driven directly by the pointer. Introducing a state alongside `Fit`, inspect zoom and zoom mode would break [L8](zoom.md#3-the-laws) — no invisible modes — and is not the design.
- **Entry is the existing zoom entry.** Press-and-hold and `Ctrl+Space` remain the only ways in. What panorama metadata changes is what zoom mode *does* on entry for that image: it starts at 100% rather than the ladder's usual first stop, and the pointer looks around instead of requiring a drag.
- **Exit is the existing exit.** `Escape` peels one layer, per [L5](zoom.md#3-the-laws). Panorama display does not add a layer for `Escape` to peel.
- **The state is visible**, per [L6](zoom.md#3-the-laws). The navigator already shows where the visible region sits within the whole; a panorama is the case it exists for ([L10](zoom.md#3-the-laws)). The grading row and its vocabulary are unchanged.

Open decisions, each of which must be answered in [zoom](zoom.md) before code is written, since they change what the user can predict:

- **What qualifies as a panorama.** Nothing in `src/` reads the XMP `GPano` namespace today; the only current panorama signal is a genre string in [app_text.h](../src/app_text.h) and [model_index.cpp](../src/model_index.cpp), which is a keyword, not a projection. The candidates are the `GPano` properties written by phone panorama modes and stitchers, an aspect-ratio threshold, or both — and an aspect threshold alone will claim images that are merely wide.
- **Whether projection is honoured.** `GPano:ProjectionType` of `equirectangular` describes a sphere, not a flat strip. Reprojecting is a different renderer; drawing the strip flat at 100% is the [rendering tiers](zoom.md#4-rendering-tiers) that already exist. These are not the same feature and the release should claim only the one it ships.
- **What "look around using the mouse" means precisely.** Pointer position mapping to center is not drag-panning, and it interacts with [L1](zoom.md#3-the-laws) anchoring, with pointer capture, and with the [inspect zoom](zoom.md#21-two-magnified-states-one-zoom) press-and-hold gesture that is already bound to the same button.
- **Vertical behaviour.** A panorama taller than the viewport at 100% has a second axis; one shorter than it does not, and pinning it is the difference between looking around and jitter.

Constraints that are already settled and are not open:

- Detection reads metadata, so it is Source work. Nothing about it may run on the UI thread or inside a Paint function.
- [L11](zoom.md#3-the-laws) still binds: input responds within one frame from pixels already held, so a panorama that has not finished decoding looks around at reduced quality rather than stalling.
- [L12](zoom.md#3-the-laws) still binds: a provisional stand-in is marked as one.

### 2. Linux support, stage one

**Owned by [Linux port](linux.md).**

[linux.md](linux.md) establishes that the platform boundary holds and that the expensive, easy-to-get-wrong work is the Windows assumptions still sitting in portable code. Its staging says those can all be fixed on Windows before any Linux file exists, as `Internal` changes proved by `.\dd.ps1 test`. Stage one deliberately departs from that in one respect, because taken literally it is unprovable:

**A Linux compile comes first, because it is the only thing that can prove the rest.** `.\dd.ps1 test` on Windows cannot detect a 32-bit `wchar_t` — that is the entire point of the `char16_t`/`char32_t` work, and MSVC is the toolchain where the defect is invisible by construction. The same argument applies to every unrecognised `#pragma`, every SAL annotation and every `__declspec`. Doing the portability fixes before a Linux compile exists means making blind changes to EXIF and ICC string decoding, validated only where the bug cannot appear.

So stage one is a minimal Linux build under WSL, and then the portable-code fixes it makes provable. It ships in 1.27.2 as a release with no observable behaviour change on Windows:

- **A minimal Linux build of `src/`, enough to run the existing suite headless.** Not the full port of 27 vendored libraries; enough to compile and link `/test`. [linux.md](linux.md#wsl-as-the-early-development-target) already names the headless suite as the highest-value early milestone — this makes it the entry to the stage rather than its exit.
- **`wchar_t` is assumed to be UTF-16.** `char16_t` for genuine UTF-16 data and `char32_t` for code points, in [metadata_exif.cpp](../src/metadata_exif.cpp), [metadata_icc.cpp](../src/metadata_icc.cpp), [app_sidebar.h](../src/app_sidebar.h) and [files_core.cpp](../src/files_core.cpp). Strictly better on Windows too.
- **`std::wstring` out of the platform interface.** `to_file_system_path`, `to_shell_path`, `create_segoe_md2_icon` and the `probe_drag_data_object` result put a Windows string type in [platform.h](../src/platform.h); the cross-platform interface should speak UTF-8 `df::file_path` only.
- **Path semantics.** [util_path.h](../src/util_path.h) encodes drive letters, UNC prefixes, the Windows illegal-character set, and — the consequential one — case-insensitive comparison that reaches the index, the search postings, deduplication and every "is this the same file" decision. [linux.md](linux.md#windows-assumptions-still-in-portable-code) names this the highest-risk item in the port, and [the case-sensitivity axis](linux.md#the-axes-that-actually-vary) rules out a build-time answer, because a single collection can span a case-sensitive home, a case-folded directory and a mounted NTFS volume. This needs a deliberate answer, not a compile fix, and it may not land in this release.
- **D3D11VA out of the media layer.** [av_format.cpp](../src/av_format.cpp) selects `AV_HWDEVICE_TYPE_D3D11VA` directly, which is a boundary violation today under the [platform rule](../AGENTS.md#working-rules) and the natural place for a VAAPI branch tomorrow. It becomes a platform-supplied hardware-decode descriptor.
- **Splitting the software rasterizer from its present path.** [linux.md](linux.md#what-each-layer-costs) argues this is the shortest route to pixels on Linux and is a pure `Internal` refactor doable on Windows today, validated by the existing `probe_software_tiling`. It turns "write a Linux renderer" into "write a Linux window that owns a BGRA buffer".
- **Small residue.** `__declspec(selectany)` in [util_date.h](../src/util_date.h), and the `error_atl_direct3d` string id in [app_text.h](../src/app_text.h) that names a Windows technology in user-visible text.

What stage one does **not** include, and what it is worth saying plainly so the release is not over-claimed: there is no Linux window, no renderer, no desktop integration and no packaging. WSL proves the portable core and the build; it proves nothing about integration with a desktop, and everything in [features with no Linux equivalent](linux.md#features-with-no-linux-equivalent) is untouched. The minimal build is also not the full [build system](linux.md#build-system) — that remains a description for `src/` plus 27 vendored libraries whose upstream build files were deliberately removed, and it collides with the current [third-party policy](third-party.md), which a later stage must update.

The milestone that closes stage one is the existing suite passing headless under WSL: a portable core proved on a second toolchain, before any window exists.
