# Diffractor 1.27.2

Baseline: 1.27.1, shipped from `master` at `2742e66d`.

**Status: in progress.** This document is the release record for 1.27.2 and states what the release changes for the user, plus its verification record. Nothing below is shipped until it appears under [Changes](#changes) with a verification entry. GitHub issues remain authoritative for issue state and discussion; the linked documents own the durable behaviour. Work deferred past this release, issues awaiting reporter confirmation, and validation still to run belong in [post-release context](v-next.md).

1.27.2 was scoped as an interim release: the first stage of the Linux port, which changes nothing a Windows user can observe, plus a small set of bounded defect fixes. It is no longer that. Three subjects that were written down as 1.27.3's — the date vocabulary, the sidebar globe, and the verbose metadata pane — were built during it, and panorama display has been pulled forward deliberately because it shares one re-index with the dates. What remains in [1.27.3](v-1.27.3.md) is the Linux window and text stack.

The consequence is that this release is no longer cheap to attribute, and the plan below is arranged so that it can still be attributed in pieces: the build migration, the dates, and the view work each land as their own change with their own verification, and each names what it would look like if it were wrong.

## Planned

### 1. Dates: one vocabulary, and a ladder that matches what the words mean

**Owned by [design](design.md) for what the user sees, and [metadata](metadata.md#dates) for which tag feeds it.**

Dates have produced more reports than any other subject — [#184](https://github.com/diffractor/diffractor/issues/184), [#192](https://github.com/diffractor/diffractor/issues/192), and the "click to open finds nothing" symptom in the same thread. The vocabulary and the resolver are built; what this section still owes is listed here, and each item is a user-visible answer rather than a refactor.

**Three dates, named for what a user already believes.** **Original** is when the content was made, **Created** when the file was made, **Modified** when it last changed. The words avoid photographic vocabulary because a collection holds scanned paintings, contracts and screen recordings as readily as photographs.

#### 1.1 Modified is a fact about the file, so the file answers it

This is a correction to the authority table as first written, and it is the one date decision that would have shipped wrong.

The table ranked `EXIF DateTime` and `XMP xmp:ModifyDate` **above** the filesystem's modified stamp. A user who edits a file today and sees Modified report 2019 has been told something false, and the report would be right: a metadata modify tag records when some *tool* last wrote the metadata, which a copy preserves and which an editor that does not maintain the tag never touches. It is not the same fact.

The rule that settles the whole table, rather than settling one row:

> **A concept is answered by whatever is authoritative for the thing the concept describes.**

- **Original** and **Created** describe the *content*. The filesystem knows nothing about content, so metadata outranks it, and the filesystem stamp is the last resort.
- **Modified** describes the *file*. The filesystem is not a fallback for it — it is the only thing that tracks an actual edit. So `File modified` becomes authority 1 for Modified, and the two metadata modify tags rank below it, answering only where there is no usable stamp, such as a remote item or an unhydrated placeholder.

The asymmetry between Created and Modified is principled rather than accidental, and stating why is what stops the table drifting again: **copying a file destroys its creation stamp and preserves its modification stamp.** So metadata wins for Created and the filesystem wins for Modified.

This also prevents a silent regression that was already loaded. `modified:` searches and Sort by Date modified read the filesystem stamp today; had the pack shipped with the table as written, both would quietly have started answering from a metadata tag.

#### 1.2 Adjust dates and the metadata editor act on Original

Both dialogs offered one date and did not say which. With three, silence is no longer possible.

**Adjust dates operates on Original, and says so.** Original is the date people fix: the camera clock was wrong, the scan is filed under the day it was scanned, the holiday crossed a timezone. Created and Modified are facts about the file, and a user shifting a camera clock by two hours does not mean "and rewrite when this file was written". The dialog names the date it is changing and shows the tag each item's value resolves from, so a set with mixed provenance is visible before the shift rather than after it.

**The metadata editor edits Original only.** Created and Modified appear beside it read-only, each with its source, so the user can see what they are not editing and why. Offering to edit Created would invite the expectation that Diffractor rewrites a filesystem stamp; offering to edit Modified would be a contradiction in terms. Editing a container's own `xmp:CreateDate` is a real case and a small one, and it is deferred to [post-release context](v-next.md) rather than guessed at here.

#### 1.3 One date control, and it is ours

The Windows date picker is a platform control in a UI that has no other platform controls, it does not follow the app's own scaling or theme, and it has no Linux counterpart — so [Stage 3](linux.md#staged-plan) would have to invent one anyway.

The replacement is **a segmented field**: year, month, day, hour, minute, second, drawn as one control with separators.

- Segments are reached with `Left`/`Right`, `Tab`, or a click.
- Typed digits fill the focused segment left to right and advance when it is full.
- `Up`/`Down` and the wheel step the focused segment, and a segment that passes its bound rolls into its neighbour, because that is what a clock does. `23:59` plus a minute is the next day.
- **Month is the one segment with a drop menu**, because a month has a name and the name is what a person reads. Everything else is a number that is faster to type than to pick — a drop menu of sixty seconds is a scrolling list standing in for two keystrokes.
- Segment order and separators follow the display locale, so `2026-08-20` and `20/08/2026` are one implementation.
- Seconds appear only when the caller asks for them.

No calendar popup. A calendar is a second control with its own layout, focus, locale and keyboard problems, and the segmented field is complete without one; it is recorded in [post-release context](v-next.md) as a candidate, not as a gap.

#### 1.4 The sidebar timeline answers with the same date as everything else

The sidebar's date chart is a navigation surface: clicking a month runs a date search. If it buckets an item under one date while the items view groups it under another, the click finds nothing — which is the whole of the "click to open finds nothing" report, reappearing in the one place the user is most likely to click.

So the chart buckets on the resolved date, through the same resolver, and the search it runs on click targets the same property. The timeline is always Original-first — a timeline of a collection is a timeline of when things happened, not of when files were written — and it does not follow the items view's current group order, because a navigation surface that reshapes itself under the user is worse than one that is merely fixed.

#### 1.5 The date bubble says where each date came from

Naming the tag is what turns "the date is wrong" into a question with a visible answer, and that is the difficulty of [#184](https://github.com/diffractor/diffractor/issues/184). The hover bubble currently pushes the tag name into the time column, which is why it reads badly.

Four columns — **name, date, time, source** — with the source dimmed, because it is provenance rather than value. Rows in a fixed order: Original, Created, Modified, then the filesystem's own created and modified stamps only where they are not already the source of a row above. A date the file does not have omits its row rather than showing an empty cell. The bubble is sized by its content instead of a fixed width.

#### 1.6 What this subject still owes

- Fixtures for both files in [#184](https://github.com/diffractor/diffractor/issues/184) — the 1990 `DateTimeOriginal` scan, and the Pixel 8 file whose `photoshop:DateCreated` is ten months later than its capture time. The issue has been reported fixed twice already and must not be closed a third time without both reproducing in the suite.
- [#192](https://github.com/diffractor/diffractor/issues/192) is diagnosed but unproven; it needs its own reproduction before it can be attributed.
- The tile caption under Group by Date Created still shows the resolved date rather than the creation date, because `populate_info` is built without knowing the active order. The group header states the bucket, so nothing misfiles.
- Manual confirmation that the three orders read correctly in each display language. "Original" as a *date* is a different word from "Original" as an unedited picture in several of them, which is why it carries a `//date` disambiguation.

### 2. Panorama display, and finding panoramas at all

**Owned by [zoom](zoom.md) and [design](design.md); the attribute it reads is owned by [metadata](metadata.md).**

Pulled forward from 1.27.3 for one concrete reason: it needs a scan-time attribute on every indexed image, this release already re-reads every file for the date pack, and asking users to sit through a second full re-index one release later is not a reasonable thing to do to them.

An image carrying panorama metadata is not served by `Fit`: fitted to a browsing window a 12000x1000 stitch is a bright line. The answers to the four decisions [1.27.3 left open](v-1.27.3.md):

- **What qualifies.** XMP `GPano` properties qualify a file outright, and the scan already records which projection it declares — see [Changes](#a-file-that-says-it-is-a-panorama). Failing that, an aspect ratio of at least 2:1 **and** a long edge of at least 4000 pixels qualifies it; both are computable from dimensions the index already holds, so the shape test costs no stored field and can be reconsidered without a re-index. An aspect threshold on its own was rejected because it claims every merely-wide screenshot; adding the size floor excludes them. A wide crop of an ordinary landscape will still be claimed occasionally, and that is acceptable because being claimed only changes where zoom starts, changes nothing about the file, and is fully reversible by zooming normally. `@panorama` remains the declaration alone, because a search is an assertion about the file rather than about how it will be displayed.
- **Projection is not honoured.** `GPano:ProjectionType` of `equirectangular` describes a sphere, and reprojecting is a different renderer from the one that exists. 1.27.2 draws the strip flat at 100%. The release claims the feature it ships and not the one it resembles.
- **Look around means the pointer drives the centre.** In zoom mode on a qualifying image the initial scale is 100% rather than the ladder's first stop, and pointer position maps directly onto the source-space centre: moving from one edge of the viewport to the other sweeps the whole width. No button is held, so the press-and-hold [inspect zoom](zoom.md#21-two-magnified-states-one-zoom) gesture is untouched. Entry and exit are the existing ones; `Escape` peels one layer per [L5](zoom.md#3-the-laws), and no layer is added for it to peel.
- **Vertical is pinned unless there is something to see.** If the image at 100% is no taller than the viewport the vertical centre is fixed; if it is taller, the pointer drives that axis too. Pinning is the difference between looking around and jitter.

**`@panorama`, with `@pano` as an alias**, joins `@photo` and `@video` as a presence term, filled at scan time from the same attribute. Panoramas are otherwise unfindable: they look like photographs to every existing query.

Not open, and binding: detection reads metadata, so it is Source work and never runs on the UI thread or inside a Paint function. [L11](zoom.md#3-the-laws) still holds — input responds within one frame from pixels already held, so a panorama mid-decode looks around at reduced quality rather than stalling — and [L12](zoom.md#3-the-laws) still marks a provisional stand-in as one.

### 3. A region on the displayed picture

**Owned by [design](design.md#application-structure) and [zoom](zoom.md).** Scope: Indexed collection, Folder, Recursive folder, External folder, Search — the media preview in the Items view, in all of them.

`Ctrl` and drag on the displayed media draws a rectangle. Dragging inside it moves it. `Escape` clears it. While it exists it carries three icon buttons: **close it**, **zoom to it**, and **open Edit with it as the crop**.

The decisions that keep it predictable:

- **The rectangle lives in source space, not view space.** It survives a resize, a layout change and a zoom, for the same reason the [zoom model](zoom.md#2-the-model) keeps its centre in source space. A rectangle that slid off the subject when the window changed would be worse than no rectangle.
- **It is clamped to the picture**, and a drag beginning outside the picture does nothing at all rather than starting a rectangle that cannot be finished.
- **It does not outlive the item.** Changing the displayed item clears it. A crop region is about one picture, and carrying it forward would apply a decision to a picture the user never made it for.
- **The buttons are not drawn during a drag**, and they move outside the rectangle when it is too small to hold them, so a small region stays usable rather than being covered by its own controls.
- **`Escape` peels one layer** ([L5](zoom.md#3-the-laws)): with a rectangle it clears the rectangle, without one it does what it did before.
- **Zoom to it** is the existing region-to-viewport primitive, already covered by `Should zoom model region to viewport`. **Open Edit with it** hands the same source-space rectangle to the edit view's crop. Neither is a new model.

### 4. The selection panel shows what the item is, before what it says

**Owned by [selection controls](selection-controls.md).** Scope: all scopes — the panel reads the displayed item and nothing in it consults the scope.

The description and the streams rows are frequently below the fold. The panel guarantees that its primary block fits without scrolling, and it keeps that guarantee — but the block is composed by element order rather than by what the item is, so an unbounded description evicts whatever follows it, and a video's stream summary is what gets evicted.

The composition rule becomes: **the primary block answers "what is this", and the secondary block answers "what does it say".**

- Every item: the media, the name, and the resolved date.
- A photograph: dimensions, camera, and the exposure triple.
- A video or audio file: duration and the stream summary. What is inside the container is the question a media file raises, and answering it below the fold is the same as not answering it.
- A description appears in the primary block **bounded to a small number of lines**, with the remainder in the secondary block. An unbounded description is the actual mechanism of the complaint, and bounding it fixes the cause rather than reordering around it.

`Should fit the whole primary block when verbose is closed` is the existing guarantee and must still hold with the new composition.

### 5. The media overlay identifies, it does not summarise

**Owned by [design](design.md#application-structure).** Scope: all scopes.

In the Media view the overlay box grows with the metadata it finds and overflows the picture. The purpose of that view is to see the media, so the overlay is competing with the only thing the view exists for.

**Density follows media type, because the overlay's purpose follows media type.**

- **Photo and video:** the overlay identifies, and nothing more — name, date, rating and label. Two lines at most. Everything else is in the selection panel and the metadata pane, which is where a user goes when they are asking rather than looking.
- **Audio:** the media is not a picture, so the overlay *is* the presentation. Title, artist, album, track and duration stay.

And the invariant that stops this returning: **the overlay never exceeds a quarter of the media's height, and it truncates rather than growing.** Without a bound, the next property anyone adds re-creates the defect.

### 6. Compare mode draws the left picture distorted on entry

**Owned by [rendering](rendering.md).** Scope: all scopes.

With two scaled-down images displayed, entering compare draws the left one with the wrong shape for a short time before it corrects itself. Observed and reproducible; the cause is **not yet established**, and this document will not name one until it is.

What is known: it corrects itself without any user action, which places it in the window between the pane being laid out and the final surface arriving, and it is the left pane specifically. The first thing to establish is whether the destination rectangle for that frame is computed from the dimensions of the surface actually being sampled, or from dimensions that are not yet the final ones — a stand-in, a previous item's surface, or a default. That is a question with a yes/no answer and it should be answered before any code changes.

### 10. What the listing does after a move or a delete

**Owned by [design](design.md#guided-operations).** Scope: Folder, Recursive folder, External folder, Search.

Two reports, one subject, and they should be answered together because a user experiences them as one moment.

- **[#249](https://github.com/diffractor/diffractor/issues/249): the folder no longer reliably updates after a move.** With *Open folder after moving* disabled, moved files used to leave the listing; now they sometimes stay and sometimes go. Intermittency is the tell — the listing is being refreshed by something that races rather than by the move completing, so the fix is to make the move's completion the thing that updates the listing rather than whatever notification happens to arrive first. This is a regression against behaviour a user was relying on to sort quickly, which is why it leads.
- **[#250](https://github.com/diffractor/diffractor/issues/250): the cursor should land after the last item that left.** Moving or deleting resets the position, so a user sorting a folder has to find their place again every time. It should settle on the item that followed the removed set — the same rule [Should decide what follows an item](testing.md) already encodes for stepping — and fall back to the end of the listing when the removed set was last.

Together these are the difference between sorting a folder and re-navigating it after every action. Neither changes what a move does to a file, and neither touches the collision or recovery contract in [file I/O](file-io.md).

### 11. The sidebar history chart is a timeline of the collection

**Owned by [locations](locations.md) for the sidebar's other charts and [design](design.md#application-structure) for what the chart claims.**

[#175](https://github.com/diffractor/diffractor/issues/175) asks whether the history chart is meant to be a timeline of the whole collection, and the honest answer is that it was not one. This release makes it one, and [§1.4](#14-the-sidebar-timeline-answers-with-the-same-date-as-everything-else) is most of the reason: a chart that buckets items on a different date from the one the view groups them under is not a timeline of anything the user can see. `Should record history beyond ten years`, `Should calculate history span from start year` and `Should choose a history range that survives wrong dates` are the existing guarantees and must still hold.


## Changes

### Three dates instead of one, and the tag each came from

**Owned by [design](design.md) for what the user sees and [metadata](metadata.md#dates) for which tag feeds it.** Scope: all scopes — a file carries the same dates however it was reached.

**Original**, **Created** and **Modified** are now three first-class dates rather than one field with two meanings behind it. Each is groupable, sortable and searchable, and the properties panel names the tag each was resolved from.

- **One resolver.** Four ladders resolved "the created date" and disagreed — `item_metadata::created()`, the histogram path in [model_index.cpp](../src/model_index.cpp), `is_date_match` in [model_search.cpp](../src/model_search.cpp), and `calc_media_created` in [model_items.h](../src/model_items.h). An item could group under one day and be found under another, which is the whole of the "click to open finds nothing" report. They are one.
- **A date pack replaces the three date fields.** Every date a file carries is stored grouped by value, with a bitmask recording which tags produced each value, so the six date tags a phone writes usually cost one stored value. Adding a source becomes a bit and a table row rather than a field, a database key and four ladder edits.
- **`photoshop:DateCreated` no longer overwrites the shutter.** It is nominally a mirror of `DateTimeOriginal` and is in practice the one an image editor rewrites on save, so it is ranked last among the capture sources: it serves files that carry nothing else, and never moves a photograph to the day it was retouched. That is [#184](https://github.com/diffractor/diffractor/issues/184).
- **`EXIF DateTime` is read as a modification date.** The standard defines tag `0x0132` as the time the file last changed, and it lives in IFD0, which is walked before the Exif SubIFD. Reading it as a creation date is why an edited photograph grouped under the day of its edit.

Two changes reach existing users and both are deliberate:

- **`taken:`, `when:`, `timeline:` and `c:` repoint from the container's date to Original.** A saved `taken:2019` returns a different set afterwards. The words did not mean the container's date, so this is a correction rather than a regression — but it changes results silently, which is why it is stated here rather than left to be discovered. `created:` still means the file's creation date, and `digitized:` is folded into it.
- **Someone who chose "group by date created" is moved to Original, once.** It is what those users believed they were choosing, and disagreeing with that belief is the substance of [#184](https://github.com/diffractor/diffractor/issues/184). The migration runs on the first start after upgrade and then stops, so both orders remain separate, selectable choices that persist.

**The upgrade re-indexes in the background and keeps answering meanwhile.** The database metadata version goes to 2. Cached properties are kept and only the scan stamp is cleared, so the existing incremental scan re-reads files at its own pace while every search, group and timeline answers from the legacy values until it does. A row with no stored pack synthesises one from its legacy fields at low authority, ranked below every real source so the re-scan always replaces it. Thumbnails are keyed separately and nothing re-encodes.

**Every rung of the ladder is filled, including the ones nothing uses yet.** A re-index can only be paid for by re-reading every file, so anything the documented ladder names is read now rather than in the release that needs it. Four sources that were reserved but dead — IPTC `DateCreated`+`TimeCreated`, IPTC `DigitalCreationDate`+`DigitalCreationTime`, ID3 `TDOR`, and `GPSDateStamp`+`GPSTimeStamp` — are read, and so are the three pairs of tags that qualify an EXIF date rather than being one: `OffsetTime*` and `SubSecTime*`. The zone changes nothing displayed today, because an EXIF date is already a wall-clock reading; it is stored because it is half of recovering a zone a file never stated, and the other half is the GPS instant beside it. The fraction is what keeps two frames of a burst apart.

None of these can be applied where they are read — a qualifier may appear either side of the date it qualifies, and `OffsetTime` sits in a different directory from `DateTime` — so the EXIF walk now collects and combines once it ends, as IPTC already had to for its split date and time datasets.

### A file that says it is a panorama

**Owned by [metadata](metadata.md#panorama).** Scope: all scopes — the scan reads the file, and nothing in the decision consults the scope.

The scan now records the panorama projection a file declares in Google's `GPano` namespace, and **`@panorama`** — short spelling `@pano` — finds them. Panoramas were previously unfindable: they look like photographs to every existing query.

This rides the same re-index as the dates rather than waiting for the release that draws them, and that timing is the point. The attribute is per indexed image and can only be filled by re-reading every file, so shipping it a release later would mean asking every user to sit through a second full re-index for one byte.

Two decisions are worth stating because they are what the flag means:

- **The file's declaration, never its shape.** A 2:1 crop of a landscape is not a panorama. Anything that wants to guess from proportions can do so at query time from the dimensions the index already holds, without a stored field that then disagrees with the file.
- **The projection is stored, not a yes/no.** It costs the same byte and it is what [the release that honours equirectangular projection](v-next.md) will need — recording it now is what stops that release needing a re-index of its own. A projection this build does not recognise is still read as a panorama rather than discarded.

### The sidebar is a globe and a set of solids

**Owned by [locations](locations.md#50-the-sidebar-globe) for what the user sees, and [rendering](rendering.md#the-sidebar-globe) for how it is drawn.** Scope: all scopes.

The sidebar's flat world map is now a sphere, drawn at the same size, turned by dragging in both axes, and framed by default on the collection's own places. The hover bubble, the place-plus-radius click and the grouping guarantee are unchanged; what changes is the presentation, the gesture, and that only the near hemisphere can be aimed at. The file-type pie and the history calendar are drawn as extruded solids by the same rasteriser, each recording what every pixel shows so the pointer is matched against the silhouette rather than against the geometry it was drawn from.

**The indexed-folders section is gone, with its Customise checkbox and its setting.** A collection's folders are how it was declared, not a place worth a standing row apiece, and a folder a user does want to hand is a saved search away. This is a removal a user will notice, which is why it is listed here rather than left to be discovered in the Customise dialog.

### Verbose metadata reports what the file holds

**Owned by [selection controls](selection-controls.md#verbose-metadata-blocks).** Scope: all scopes — the pane reads the displayed item's own embedded blocks and nothing in it consults the scope.

The block inspector claimed to report the file and did not. Two libexif defaults were quietly editing what it showed, and three kinds of content it already had in hand were never presented.

- **Entries are no longer silently dropped, and entries the file does not contain are no longer invented.** libexif defaults to discarding every tag it has no name for and to supplying the mandatory tags a directory omits. The pane clears both, so a tag outside the parser's table is listed under its number and a directory reports what the file actually stored. The same default also rewrote off-spec entries in place, so a value stored as `LONG` where the standard says `SHORT` reported the standard's format and a hex dump libexif had synthesised; the pane now shows the file's own format and bytes. The write paths keep both defaults, because a file being produced should conform.
- **The maker note is read as a directory rather than reported as a blob.** Canon, Nikon, Fuji, Olympus, Sanyo, Epson, Pentax and Casio are decoded into a section named for the make. The binary entry stays beside it, and an unrecognised make keeps only that entry.
- **A `Derived` section carries the facts the camera implied but did not record** — crop factor, angle of view, circle of confusion, hyperfocal distance, light value, megapixels. Each appears only when every tag it needs is present.
- **A Multi-Picture JPEG lists the further whole images it indexes**, each with the role it declares and the extent it claims, instead of leaving them inside an anonymous APP2 row.
- **An embedded thumbnail is shown as a picture**, at its own size unless the pane is narrower, and open without being asked. A hex dump is now what a payload falls back to when it cannot be decoded, and a dump never opens unasked. Decoding happens where the block is built, never while painting.

Two defects were found while reviewing this work and fixed with it:

- **A crafted Multi-Picture segment could read outside the file's buffer.** The new index parser bounds-checked file-supplied 32-bit offsets with 32-bit arithmetic, so an offset near the top of the range wrapped past the check. The arithmetic is now done in 64 bits, matching the guard `exif_data_buffer` already uses for the same reason.
- **Cover art kept a texture belonging to a lost graphics device.** `cover_art_control` cached a texture and forwarded `free_graphics_resources` to its children without releasing its own, so a device loss or a downgrade to software rendering left it holding a dead resource. Both it and the new image row now release on that event.

### One build, on both platforms

**Owned by [Linux port](linux.md#retiring-msbuild).** No observable behaviour change on Windows, which was the entire requirement: the same product, produced by a different build.

`df.sln`, `src/app.vcxproj` and the 26 vendored `.vcxproj` files are gone. CMake is the only description of the tree, on both platforms, and `tools/lint_repo.ps1` fails a tracked `.sln` or `.vcxproj` so a second one cannot return quietly. Two descriptions of one tree had already drifted twice, each time silently and each time changing which media formats decode.

The timing is the point rather than a convenience. 1.27.3 introduces a Linux window; a build system carrying a shipped product for the first time on that same release would put two new things in one failure path. Windows exercises it for a release first.

The migration was judged on agreement rather than on both builds succeeding, and at the point the two were compared they compiled the same 88 translation units and agreed on every define. What differed is recorded and explained in [tools/build-divergence.txt](../tools/build-divergence.txt), including the one risk that could have reached a user silently: the build targets an SSE2 baseline and dispatches AVX2 at run time through `platform::has_avx2`, so a build that raised the baseline would pass every test on every machine that runs tests and fault on the machines least able to report why. It did not.

Three defects surfaced that had nothing to do with the build system and would not otherwise have been found:

- **The Linux CI matrix had been building Debug twice.** `tools/dd.py` took its trailing arguments with `argparse.REMAINDER`, which swallows the script's own options, so `dd build --config Release` silently built Debug. Both legs of the matrix were the same build.
- **The Store configuration did not compile.** A `std::wstring_view` overload removed during the port left one call site behind `#ifdef WINSTORE` with nothing compiling it, and nothing had built that configuration since.
- **The 32-bit build was only ever described for x64.** It assembled the x86-64 libjpeg SIMD as 32-bit objects, pre-included FFmpeg's x64 assembler configuration, and omitted the define that gives every 32-bit symbol the underscore MSVC expects.

Windows CI now builds Debug and Release x64, Release Win32 and the Store binary, and runs the suite on each — the first time any commit has built CMake on Windows, or built the Store binary at all.

Opening this pull request also ran [linux.yml](../.github/workflows/linux.yml) against the port for the first time, because it triggers on `master` and on pull requests targeting it, and the Linux work has only ever lived on a release branch. It found three things a developer machine cannot see, all of the same kind — the machine, rather than the build description, was deciding the answer:

- `libarchive` and `libwebp` were both reached through the spelling their *system* package installs, so the fully vendored build CI runs — which has neither `-dev` package — could not resolve their headers. Both are now reached through the vendored tree, which is what Windows has always done.
- The FFmpeg configuration comparison failed on two documentation switches. They are autodetected from whether `perl` and `texi2html` are installed, so one side being a checked-in artifact and the other being generated wherever the build runs made the comparison report a package list as a product difference. Nothing they control is built on either platform, so the comparison now excludes them.

The FFmpeg and XMP forks stopped being optional at the same time. Both build under GCC, and a configuration that dropped them produced an application reporting every media file and every XMP property as absent, which is not Diffractor. Configuration now fails when either is missing, and the 345 lines of stand-in translation units behind them are deleted.

### Linux support, stage one

**Owned by [Linux port](linux.md).** No observable behaviour change on Windows.

[linux.md](linux.md) establishes that the platform boundary holds and that the expensive, easy-to-get-wrong work is the Windows assumptions still sitting in portable code. Stage one departs from that staging in one respect, because taken literally it is unprovable: **a Linux compile comes first, because it is the only thing that can prove the rest.** `.\dd.ps1 test` on Windows cannot detect a 32-bit `wchar_t` — that is the entire point of the `char16_t`/`char32_t` work, and MSVC is the toolchain where the defect is invisible by construction.

What landed:

- **The portable core builds and passes its whole suite on Linux**, in both configurations, under GCC 13. All 26 vendored libraries build, CMake describes the whole tree for both platforms, and [linux.yml](../.github/workflows/linux.yml) guards it on every commit.
- **Path identity follows the filesystem.** Case-insensitive comparison reached the index, the search postings, deduplication and every "is this the same file" decision, and it was baked into the interned string hash rather than only into a comparison. It is now a compile-time property: case-sensitive off Windows, unchanged on it. Identity stayed separate from type, so file-type, extension and sidecar matching still fold case on both platforms.
- **`wchar_t` is no longer assumed to be UTF-16**, and `std::wstring` is out of the platform interface. The gate that once found 28 files finds 9, and every one of those is the UTF-16 boundary itself, its tests, or a native type named where it belongs.
- **The CPU rasterizer is portable code**, with GDI behind a present-target interface and the glyph path taking a coverage bitmap rather than a font type. Both backends now share a `ui::draw_context_device` that names no graphics API.
- **The two platforms' rendering is compared rather than assumed.** A reference scene is rasterised with no window and no font and checked against recorded pixels — the first thing that has ever compared the two rasterizers instead of asserting they agree.
- **D3D11VA is out of the media layer**, replaced by a platform-supplied hardware-decode descriptor: a boundary violation removed today, and where a VAAPI branch goes tomorrow.
- **The icon font is one the app is allowed to ship.** Segoe MDL2 was checked in and embedded in the shipped binary despite being a Windows system font whose licence does not permit redistribution. It is replaced on both platforms by Fluent UI System Icons, which also resolved three glyph collisions — Cut and Copy drew identically, and a file move drew exactly like folder navigation.

What stage one deliberately does **not** include: there is no Linux window, no renderer, no desktop integration and no packaging. WSL proves the portable core and the build; it proves nothing about integration with a desktop, and everything in [features with no Linux equivalent](linux.md#features-with-no-linux-equivalent) is untouched.

### Go to parent folder sits with Back and Forward

**Owned by [design](design.md#application-structure).** Scope: all scopes — the toolbar is the same in every one, and the command's availability, binding and effect are untouched.

Go to parent folder was in the second toolbar group, beside Favourites and the collection options, while the two commands it is used with sat in the first. It also drew a folder with an arrow, which reads as something done to a folder rather than as a move through the tree. It now follows Forward and draws a plain up arrow, matching the group it is in.

### The date direction is one option, and no longer looks like a sort key

**Owned by [design](design.md#command-availability).** Scope: all scopes.

*Sort dates descending* appeared permanently ticked. It was one of two adjacent items — *Sort dates descending* and *Sort dates ascending* — that between them expressed a single yes/no choice, so exactly one of the two was always ticked, and clicking the ticked one set the value it already had and did nothing. Descending is the default, so the first of the pair is ticked from first run and cannot be cleared where it stands.

Both were also sitting inside the *Sort by* list, which reads as a set of sort keys — name, size, date created, date modified. Direction is not a key, and being listed among them invited the reading that it was one. *Ascending* and *descending* made that worse: for dates the words are genuinely ambiguous, because half of readers take ascending to mean the date value ascends and half take it to mean recency does, and nothing on screen settles it.

There is now one item, **Show newest items first**, below the sort keys and beside *Show items in random order*. Ticked means newest first, unticked means oldest first, and clicking it always changes something. It names the outcome a user can check against the screen rather than the direction a comparator runs, and it contains no form of the word *sort*, so it cannot be mistaken for a sixth sort key. All thirteen catalogs are updated. The empty-results surface is unaffected: it offers whichever direction is not current, by name, as an action rather than a state.

### An edge between the address bar and the surface that scrolls

**Owned by [design](design.md#application-structure).** Scope: Indexed collection, Folder, Recursive folder, External folder, Search — the items view draws it in all of them.

The address bar and the items view share a background, so with nothing between them the two read as one surface and it is not obvious which part scrolls. A single line now separates them. Nothing moves: it is drawn over the top row of the view rather than taking space from it.

### A very large JPEG no longer draws green

**Owned by [file I/O](file-io.md#4-reading-the-display-phase-ladder).** Scope: all scopes — the ladder decodes an image the same way whichever scope it was reached from, and nothing in the decision reads the scope.

A photograph large enough for the ladder to decode it at its smallest scale drew solid green if it carried 4:2:2 or 4:4:4 chroma — the subsamplings that keep full vertical chroma resolution. At that scale the decoder is handed one row per call, and it was averaging two chroma rows out of a buffer holding one while indexing them by position within the call rather than within the image. Half of every chroma sample therefore came from memory nothing had written, and an unwritten chroma pair is exactly the value that renders green.

4:2:0, which most cameras write, returns two rows per call and was never affected, which is why the defect followed particular files rather than the whole collection. Smaller images are decoded at a coarser scale or none at all and were also unaffected.

### Fixed, and confirmed by the reporter

Both were fixed in code already in this branch and have been confirmed against `1.27.1.1275`:

- **Ratings and labels on a network drive** ([#207](https://github.com/diffractor/diffractor/issues/207)) — rating or labelling a photo on a NAS failed and left a `diffractor_` file beside it. This one was labelled a risk of silent data loss.
- **Rating a photo no longer changes which date it groups under** ([#192](https://github.com/diffractor/diffractor/issues/192)).

## Release readiness

A review of the branch against `master` on 2026-08-19 found eight things standing between it and a release. Each is recorded with its disposition, because several were invisible from a green local build.

**Fixed during the review:**

- **The order migration ran at every start.** The [#184](https://github.com/diffractor/diffractor/issues/184) remap from Date created to Original was applied on every `load_options`, while `save_options` wrote the user's choice back — so Group by and Sort by *Date created* could never be persisted, and the order the migration moved away from was unreachable. Options now carry a version, the remap runs once against version 0, and both orders stick. Migrating on every start is the general shape of this bug: a translation applied without a record that it has been applied is a translation that never stops.
- **The date-pack upgrade reported a success it had not achieved.** It materialised the whole `item_properties` table into two string vectors to test each name's file type, then issued one `UPDATE` per row while ignoring every result, and returned `true` unconditionally — so `PRAGMA user_version = 2` was stamped even when nothing had been cleared, and those users would never have received a date pack at all. It is now the single statement the invalidation beside it always was: one result to check, nothing to hold in memory, and no way to half-succeed. Re-reading the few file types that carry no metadata costs less than the materialisation it replaces.
- **The lint failed on a document that is not in the repository.** `doc-ownership` walked the filesystem, so a private working note in `docs/` — ignored, excluded, or merely not added yet — failed the gate for having no owner row. Every doc rule now considers only what git tracks. A permanently red gate is worse than no gate: it makes a real ownership violation indistinguishable from the noise.

**Closed by committing and pushing this branch:**

- **`src/model_dates.h` was untracked** while [model_property.h](../src/model_property.h) includes it and [metadata](metadata.md) links it. The branch built only because the file existed on one disk; a fresh clone could not have compiled, and `doc-code-anchors` would have failed in CI.
- **Roughly 1730 lines across 43 files were uncommitted** — the date pack, the database migration, the EXIF and Multi-Picture work, the scaled-JPEG chroma fix, the perceptual-hash transpose and the postings radix sort. None of it was on a commit and none had been through CI.
- **The last four commits post-dated the last green CI run**, including the globe and the sidebar rewrite. All three Windows shipping configurations were built and run locally against them — x64 Release, x86 Release and the Store binary, 791 of 791 each — but Linux had not been built since, and those commits removed code from [render_surface.cpp](../src/render_surface.cpp) and [model_index.cpp](../src/model_index.cpp).

**Answered by this document:**

- **The release documents described a different release.** The notes deferred the date vocabulary to 1.27.3 and stated that nothing would be renamed, while the branch renamed the capture date, repointed four search words, added two orders and bumped the database version; 1.27.3 still claimed the globe and the dates as its own. The scope is now where the code is.
- **A user-visible removal was undocumented.** The indexed-folders sidebar section, its setting and its Customise checkbox were deleted in the last commit with only [design](design.md#application-structure) updated. It is now under [Changes](#the-sidebar-is-a-globe-and-a-set-of-solids).

**Carried, with a gate rather than a fix:**

- **The sidebar now rasterises on the UI thread.** The globe costs roughly 0.4 ms per frame at 100% scaling and 2 ms at 200%, and the pie is re-rasterised whenever the pointer crosses a wedge. Correct by construction — it is redrawn only when the view or the extent changed — but unmeasured under a sustained drag at the widest sidebar and highest scaling, which is a manual gate below.
- **The date pack is 61 bytes resident per indexed file** against 24 for the three fields it replaces, which is +37 MB per million files. Accepted for x64; it is listed as a manual gate on the 32-bit build, where address space is already the scarce resource.
- **`.vscode/tasks.json` still drives MSBuild against `df.sln`**, which this release deleted. Every build task in the workspace is dead. Not a shipping defect and not a user-visible one, so it is carried in [post-release context](v-next.md).
