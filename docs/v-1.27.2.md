# Diffractor 1.27.2

Baseline: 1.27.1, shipped from `master` at `2742e66d`.

**Status: in progress.** This document is the release record for 1.27.2 and states what the release changes for the user, plus its verification record. Nothing below is shipped until it appears under [Changes](#changes) with a verification entry. GitHub issues remain authoritative for issue state and discussion; the linked documents own the durable behaviour. Work deferred past this release, issues awaiting reporter confirmation, and validation still to run belong in [post-release context](v-next.md).

1.27.2 is an interim release. It carries the first stage of the Linux port, which changes nothing a Windows user can observe, together with a small set of defect fixes. The two subjects that need a design answer before code — panorama display and the date vocabulary — are deferred to [1.27.3](v-1.27.3.md), so that the port's largest and least visible change ships on its own and can be attributed on its own if something turns out to be wrong. Every fix it carries is small and precisely bounded for the same reason: this release should be cheap to attribute, not full.

## Planned

### 1. A date that survives an edit

**Owned by [metadata](metadata.md).**

[#184](https://github.com/diffractor/diffractor/issues/184) is confirmed still present in `1.27.1.1275`. Editing a photograph moves it to today under Group by date created, and Click to open then looks for it under a date it was never taken.

The cause is one field carrying two concepts. [metadata_xmp.cpp](../src/metadata_xmp.cpp) reads XMP `photoshop:DateCreated` into `created_exif`, the same field EXIF `DateTimeOriginal` uses, and XMP is parsed after EXIF. `photoshop:DateCreated` is nominally a mirror of `DateTimeOriginal`, but it is the one an editor rewrites: the reporter's file carries `photoshop:Credit: Edited with Google AI` and a `photoshop:DateCreated` ten months later than its `DateTimeOriginal`. So the edit time overwrites the capture time.

The fix for this release is the proximate one: `photoshop:DateCreated` fills the capture date only when no better source has, because it is the lowest-authority capture source precisely by being the one editors rewrite. The two disagreeing precedence chains — `item_metadata::created()` in [model_property.h](../src/model_property.h) and the timeline path in [model_index.cpp](../src/model_index.cpp) — collapse onto one at the same time.

What this release does **not** do is rename anything. The deeper problem is that the property a user sees as "created" is the container's date while the capture date hides behind "created.exif", and that `taken:` searches the former. That is [1.27.3's subject](v-1.27.3.md#2-one-date-vocabulary), because it is user-visible, changes what a saved search returns, and touches every translation catalog.

### 2. Video that ignores its aspect ratio

**Owned by [rendering](rendering.md).**

[#78](https://github.com/diffractor/diffractor/issues/78) has had the sample aspect ratio applied in [av_format.cpp](../src/av_format.cpp), so the scan reports display dimensions rather than the stored frame size, and `exe/test/anamorphic.mp4` covers it. The issue is nevertheless still open, and the original report is about the *displayed* picture rather than the reported dimensions.

This release's first task is therefore verification rather than code: establish whether a file that still reproduces exists, and whether any remaining defect is in the display path rather than the scan. If it reproduces, the fix belongs here; if it does not, the issue closes naming the build that resolved it.

### 3. Small reported defects

Each is diagnosed to the line in [post-release context](v-next.md#14-issues-still-open) from source evidence alone, so neither needs manual reproduction time to start.

- **A presence badge that says "1"** ([#137](https://github.com/diffractor/diffractor/issues/137)). The duplicate badge is formatted with `show_zero = true` and has no suppression for a count of one, in the item list or the title overlay, so it reports a number that tells the reader nothing. **Owned by [collections](collections.md).** The one thing to settle before changing it is what the count means at 1 — the item alone, or one other copy — because that decides whether the threshold is 1 or 2.
- **Completing a path that contains spaces produces a broken search** ([#139](https://github.com/diffractor/diffractor/issues/139)). `auto_quote_search_input` in [model_search.cpp](../src/model_search.cpp) quotes a whole input, but the completion path concatenates the lead and the folder text with a space and never quotes, so accepting a completion for a folder like `C:\My Photos` yields something the parser reads as two terms. **Owned by [design](design.md#navigation-and-search).** `should_preserve_and_auto_quote_search_input` already exists and is the place to extend.

### 4. Confirm and close

No code expected. Several reports are already satisfied by shipped behaviour and are open only because nothing has confirmed them against a real file or a real session. Each needs one manual pass, and each either closes naming the build or turns into a real defect with a known reproduction.

## Changes

### One build, on both platforms

**Owned by [Linux port](linux.md#retiring-msbuild).** No observable behaviour change on Windows, which was the entire requirement: the same product, produced by a different build.

`df.sln`, `src/app.vcxproj` and the 26 vendored `.vcxproj` files are gone. CMake is the only description of the tree, on both platforms, and `tools/lint_repo.ps1` fails a tracked `.sln` or `.vcxproj` so a second one cannot return quietly. Two descriptions of one tree had already drifted twice, each time silently and each time changing which media formats decode.

The timing is the point rather than a convenience. 1.27.3 introduces a Linux window; a build system carrying a shipped product for the first time on that same release would put two new things in one failure path. Windows exercises it for a release first.

The migration was judged on agreement rather than on both builds succeeding, and at the point the two were compared they compiled the same 88 translation units and agreed on every define. What differed is recorded and explained in [tools/build-divergence.txt](../tools/build-divergence.txt), including the one risk that could have reached a user silently: the build targets an SSE2 baseline and dispatches AVX2 at run time through `platform::has_avx2`, so a build that raised the baseline would pass every test on every machine that runs tests and fault on the machines least able to report why. It did not.

Three defects surfaced that had nothing to do with the build system and would not otherwise have been found:

- **The Linux CI matrix had been building Debug twice.** `tools/dd.py` took its trailing arguments with `argparse.REMAINDER`, which swallows the script's own options, so `dd build --config Release` silently built Debug. Both legs of the matrix were the same build.
- **The Store configuration did not compile.** A `std::wstring_view` overload removed during the port left one call site behind `#ifdef WINSTORE` with nothing compiling it, and nothing had built that configuration since.
- **The 32-bit build was only ever described for x64.** It assembled the x86-64 libjpeg SIMD as 32-bit objects, pre-included FFmpeg's x64 assembler configuration, and omitted the define that gives every 32-bit symbol the underscore MSVC expects.

Windows CI now builds Debug and Release x64, Release Win32 and the Store binary, and runs the suite on each — the first time any commit has built CMake on Windows, or built the Store binary at all.

Opening this pull request also ran [linux.yml](../.github/workflows/linux.yml) against the port for the first time, because it triggers on `master` and on pull requests targeting it, and the Linux work has only ever lived on a release branch. It found three things a developer machine cannot see, all of the same kind — the machine, rather than the build description, was deciding the answer:

- `libarchive` and `libwebp` were both reached through the spelling their *system* package installs, so the fully vendored build CI runs — which has neither `-dev` package — could not resolve their headers. Both are now reached through the vendored tree, which is what Windows has always done.
- The FFmpeg configuration comparison failed on two documentation switches. They are autodetected from whether `perl` and `texi2html` are installed, so one side being a checked-in artifact and the other being generated wherever the build runs made the comparison report a package list as a product difference. Nothing they control is built on either platform, so the comparison now excludes them.

The FFmpeg and XMP forks stopped being optional at the same time. Both build under GCC, and a configuration that dropped them produced an application reporting every media file and every XMP property as absent, which is not Diffractor. Configuration now fails when either is missing, and the 345 lines of stand-in translation units behind them are deleted.

### Linux support, stage one

**Owned by [Linux port](linux.md).** No observable behaviour change on Windows.

[linux.md](linux.md) establishes that the platform boundary holds and that the expensive, easy-to-get-wrong work is the Windows assumptions still sitting in portable code. Stage one departs from that staging in one respect, because taken literally it is unprovable: **a Linux compile comes first, because it is the only thing that can prove the rest.** `.\dd.ps1 test` on Windows cannot detect a 32-bit `wchar_t` — that is the entire point of the `char16_t`/`char32_t` work, and MSVC is the toolchain where the defect is invisible by construction.

What landed:

- **The portable core builds and passes its whole suite on Linux**, in both configurations, under GCC 13. All 26 vendored libraries build, CMake describes the whole tree for both platforms, and [linux.yml](../.github/workflows/linux.yml) guards it on every commit.
- **Path identity follows the filesystem.** Case-insensitive comparison reached the index, the search postings, deduplication and every "is this the same file" decision, and it was baked into the interned string hash rather than only into a comparison. It is now a compile-time property: case-sensitive off Windows, unchanged on it. Identity stayed separate from type, so file-type, extension and sidecar matching still fold case on both platforms.
- **`wchar_t` is no longer assumed to be UTF-16**, and `std::wstring` is out of the platform interface. The gate that once found 28 files finds 9, and every one of those is the UTF-16 boundary itself, its tests, or a native type named where it belongs.
- **The CPU rasterizer is portable code**, with GDI behind a present-target interface and the glyph path taking a coverage bitmap rather than a font type. Both backends now share a `ui::draw_context_device` that names no graphics API.
- **The two platforms' rendering is compared rather than assumed.** A reference scene is rasterised with no window and no font and checked against recorded pixels — the first thing that has ever compared the two rasterizers instead of asserting they agree.
- **D3D11VA is out of the media layer**, replaced by a platform-supplied hardware-decode descriptor: a boundary violation removed today, and where a VAAPI branch goes tomorrow.
- **The icon font is one the app is allowed to ship.** Segoe MDL2 was checked in and embedded in the shipped binary despite being a Windows system font whose licence does not permit redistribution. It is replaced on both platforms by Fluent UI System Icons, which also resolved three glyph collisions — Cut and Copy drew identically, and a file move drew exactly like folder navigation.

What stage one deliberately does **not** include: there is no Linux window, no renderer, no desktop integration and no packaging. WSL proves the portable core and the build; it proves nothing about integration with a desktop, and everything in [features with no Linux equivalent](linux.md#features-with-no-linux-equivalent) is untouched.

### Go to parent folder sits with Back and Forward

**Owned by [design](design.md#application-structure).** Scope: all scopes — the toolbar is the same in every one, and the command's availability, binding and effect are untouched.

Go to parent folder was in the second toolbar group, beside Favourites and the collection options, while the two commands it is used with sat in the first. It also drew a folder with an arrow, which reads as something done to a folder rather than as a move through the tree. It now follows Forward and draws a plain up arrow, matching the group it is in.

### A checked command's tick now follows the setting it reports

**Owned by [design](design.md#command-availability).** Scope: all scopes.

Choosing Sort dates ascending re-sorted the view but left the tick on Sort dates descending, so that option read as permanently checked. The command state is re-read only on one invalidation flag, and the path that changes a setting did not raise it, so a tick stayed wherever it was until some unrelated command happened to raise the flag.

Every command that changes a setting directly had this: sort dates ascending and descending, highlight large items, show sidebar, scale up, show rotated, verbose metadata and raw preview. Found by manual testing.

### An edge between the address bar and the surface that scrolls

**Owned by [design](design.md#application-structure).** Scope: Indexed collection, Folder, Recursive folder, External folder, Search — the items view draws it in all of them.

The address bar and the items view share a background, so with nothing between them the two read as one surface and it is not obvious which part scrolls. A single line now separates them. Nothing moves: it is drawn over the top row of the view rather than taking space from it.

### Fixed, and confirmed by the reporter

Both were fixed in code already in this branch and have been confirmed against `1.27.1.1275`:

- **Ratings and labels on a network drive** ([#207](https://github.com/diffractor/diffractor/issues/207)) — rating or labelling a photo on a NAS failed and left a `diffractor_` file beside it. This one was labelled a risk of silent data loss.
- **Rating a photo no longer changes which date it groups under** ([#192](https://github.com/diffractor/diffractor/issues/192)).

## Verification

Recorded so far; completed on release.

- `.\dd.ps1 test`: 756 x64 Debug / 762 x64 Release, 0 failures; 13 catalogs, 1187 source strings, 0 structural problems. The six-test difference between configurations is the decoder fuzz and closest-location tests, which are `#ifndef _DEBUG`.
- Linux: 738 of 738 under GCC 13, Debug and Release. The count differs from Windows because `_DEBUG` is an MSVC macro, so Linux runs those six guarded tests in both configurations, and because the Windows-only platform tests do not exist there.
- New tests for the port work: path identity follows the filesystem and agrees with its own hash; tiled rasterisation matches the whole surface; one reference scene rasterises to the same pixels on every platform; and the software buffer stays bounded as the client grows. Each was verified discriminating by breaking the rule and re-running — the parity gate by mirroring one blit, which moved three of its 24 samples outside tolerance.
- The parity gate compares within a tolerance rather than by hash, and the reason is recorded in [rendering](rendering.md#the-software-tile): an exact digest of that scene is identical between MSVC and GCC but *not* between MSVC Debug and Release, so an exact artifact would fail for a reason the code does not own.
- Still to record: version stamps agreeing at `1.27.2` across [src/app.cpp](../src/app.cpp), [src/platform_win_res.rc](../src/platform_win_res.rc), [src/platform_win.manifest](../src/platform_win.manifest), [installer/diff.nsi](../installer/diff.nsi) and [exe/AppxManifest.xml](../exe/AppxManifest.xml); and the tests for the planned fixes above.
- The build migration, recorded: all four Windows binaries produced by CMake under their shipped names in `exe/` — `diffractor64-d` 758 of 758, `diffractor64` 764 of 764, `diffractor32` 764 of 764, and the Store `diffractor` 764 of 764, with the `WINSTORE` define confirmed discriminating by the update string being present in the desktop binary and absent from the Store one. The two builds compiled the same 88 translation units and shared five defines; every difference is listed in [tools/build-divergence.txt](../tools/build-divergence.txt) and the SSE2 baseline is unchanged. `.\dd.ps1 test` green end to end with no MSBuild involved.
- Windows CI, recorded: [windows.yml](../.github/workflows/windows.yml) green on Debug x64, Release x64, Release Win32 and the Store binary — the first CI that has ever built CMake on Windows.
- Still to record for the build migration: a green [linux.yml](../.github/workflows/linux.yml) run against a fully vendored image, which is the check that found the `libarchive` and `libwebp` include paths and is the only thing that can confirm no third is behind them; and one `.\dd.ps1 desktop` and `.\dd.ps1 store` producing a signed installer and `.msix` from the CMake build.
- Manual gates for this release, chosen against what actually changed rather than as a sweep: rename with collisions, and copy or move onto a network share, because path identity is the change that reaches the index and the rename planner. Software rendering was checked by eye on a real window, popups included.
- Still to record: the separator line judged by eye against the address bar, which is the only thing that can settle whether it reads as an edge or as clutter.
