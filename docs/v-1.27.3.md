# Diffractor 1.27.3

Baseline: 1.27.2. **Status: planning.**

This is the plan for 1.27.3. Nothing counts as committed until it has shipped and moved out of
[Planned](#planned) into a Changes section. GitHub issues own issue state; the linked documents own
the durable behaviour. Work attached to no release belongs in [post-release context](v-next.md).

1.27.3 has two subjects: **a Linux user can see a window**, and **the one platform control left in the UI becomes ours**. The first is better alone in its own failure path — a release introducing a Linux window on the same commit as a build system carrying a shipped product for the first time would put two new things in one failure path, and [1.27.2](v-1.27.2.md) has already taken the build. The second is the half of the date control 1.27.2 built the model for and could not finish.

## Changes

### A search term the address box shows is a search term it can read back

**Owned by [design](design.md#navigation-and-search).** Scope: Search.

Four separate ways a query could be accepted and then answer the wrong set, or nothing at all. Each
was silent: no error, no empty-result explanation, just a different answer from the one asked for.

- **A media type was written out in the display language and could only be read back in English.**
  `format_term` emits the group's *translated* name — `@Foto`, `@Photos` — and `parse_file_group`
  only knew the untranslated singular. Because the current search is persisted as text and re-parsed
  at launch, a media type chosen from the sidebar in any of the twelve non-English catalogs worked
  for the session and was gone at restart, listing the whole collection instead. A saved favourite
  carrying one was broken permanently. The plural was unreadable in every language, including
  English, even though `@photos` is what the search vocabulary offers. The parser now accepts the
  canonical name, the plural, and both display forms.
- **`with:` and `without:` discarded everything the tokenizer had read except the scope.** The
  modifier was rebuilt from the polarity alone, so `-with:rating` returned exactly what `with:rating`
  returns, `with:rating or with:label` intersected instead of uniting, and an opening parenthesis was
  dropped while its closing partner survived — which flattens the whole Boolean expression. Every
  other term arm carried the modifier through; these four did not.
- **`with:orientation` matched almost everything and excluded the one orientation it names.** The
  test read `!= left_top`, which is EXIF orientation 5, rather than the default `top_left`. All three
  places that answer "does this carry an orientation" — the matcher, the date packer and the search
  presence bit — now ask the same question.
- **`with:` offered eleven scopes the matcher has no answer for.** The list is a promise that asking
  answers, and `megapixels`, `audio.channels`, `altitude`, `gps.speed` and `document.id` now keep it —
  `altitude` and `gps.speed` answer from a non-zero reading, as the presence bit already did.
  `null`, `encoding.tool`, `media.category`, `streams` and `id` are names with nothing stored behind
  them and `crc32c` is stored on the index record rather than the metadata, so none of the six is
  offered any more; `encoding.tool` also leaves the Select-term picker, which is the one surface that
  let a value be typed for it.

Two smaller ones alongside them: folder and Open With completion needed **every** word of a
multi-word query to match and stopped looking after the first, so `My Pictures` suggested nothing —
and the highlights it hands back are now in text order, because both renderers walk the string
forwards and drop anything behind them, so typing the words in the other order used to underline only
one of them. The localized `@duplicates` spellings were captured once into a function static that
points into the translation catalog, so switching language mid-session left the table describing the
old one; and the media-type spellings are now registered into the lookup table when a catalog loads
rather than compared per parse, because that parse runs on the auto-complete worker once per
candidate per keystroke.

### Losing the graphics device no longer empties a view

**Owned by [rendering](rendering.md).** Scope: All scopes — a lost device is not something the user
chose, and the recovery must not depend on which view is open.

A device loss — a driver update, a TDR, an RDP transition — permanently downgrades the session to
software rendering, and a texture built on the lost device then draws nothing at all. Three holders
had no route to hear about it:

- **The map in Locate went blank and stayed blank.** `locate_view` overrode the broadcast with an
  empty body, so the tile texture cache it inherits was never shed; and because a cache *hit* returns
  before the placeholder the miss path draws, the result was empty background rather than grey tiles.
  It now recovers on the next frame instead of only on a pan, a zoom or leaving the view.
- **Photo edit kept drawing the crop rectangle, the grid and the dimensions over nothing.** Every
  slider still appeared to work. `edit_view` now sheds its texture and reaches its three child
  elements.
- **A cluster marker was claimed by the wrong bubble.** Markers are drawn forwards, so the last is on
  top, but the hit test returned the first — clicking the bubble you can see opened the one beneath
  it wherever two overlap.

### Video that cannot take the fast path still draws

**Owned by [rendering](rendering.md).** Scope: All scopes.

- **A refused shared-texture build was silent, had no fallback, and repeated itself every frame.**
  When the cross-device bridge could not be built, video rendered nothing and no line was written to
  the log. The failure is now reported once and remembered against the device, extent and format that
  refused it, so the expensive kernel calls are not re-attempted per frame on the UI thread, and the
  frame falls through to the CPU scaler that was already written below.
- **A failed hardware-frame download drew nothing and said nothing.** The transfer result was not
  tested, so the frame stayed in a pixel format sws refuses and the whole conversion quietly answered
  false. It is now refused explicitly and reported once per scaler. A short conversion — which cannot
  arise on this path, because source and destination extents are equal — is no longer accepted as
  success either, since `alloc` does not zero and the tail would be whatever the heap last held.
- **The compare hover preview decoded two videos at full source resolution on every pointer move**,
  bypassing the texture budget, so a pair of 4K videos showed nothing at all. It now decodes to the
  extent of the pane it is drawn into.
- **The video decoder was the one decoder with no size ceiling.** The still decoder refuses an
  over-budget source twice over; `init_streams` did neither, and the index walk opens every video it
  finds. It now applies the same two gates.
- **The two backends drew different chrome.** The software backend decoded the drop-shadow artwork
  through WIC — which is optional, and whose absence is a supported degraded mode — while the
  hardware backend used the app's own PNG path. Without WIC the GPU backend kept every shadow and the
  CPU backend lost all of them, in every dialog and bubble, in every session. Both now use the same
  decoder, and a failure is latched and logged rather than retried per tile per frame.

### Smaller changes

- **Every cached checksum was destroyed on the first folder validation after startup.** A folder
  brought in from the database carries no filesystem stamp — the cached row has neither a modified
  time nor a size — and the absent stamp was read as evidence the bytes had changed. Duplicate
  detection therefore lost its byte-identical rung on every launch, reporting fewer copies after a
  restart than during the session that found them. For a node with no stamp the question is now
  answered by the scan timestamp, which *is* persisted and is the same test the rescan gate makes —
  so a file edited between sessions still clears its checksum, which is what the clear is for.
- Burn is **absent rather than dimmed** on a machine with no writer, which [design](design.md#command-availability)
  requires: dimming says "not now", and on most machines the answer is "not here". The Win32 menu
  builder now honours `visible` at all, which it never did — so the six other commands that already
  answered that way were hidden on the toolbar and greyed in the menus at the same time.
- A stored playback repeat mode outside the three defined values is rejected rather than admitted as
  an enumerator no `switch` has an arm for, matching the rule its two neighbours already apply.
- `index_state::scan_item` was the one `validate_folder` call site of eleven that dereferenced a
  documented-null result; the query worker no longer carries an owning handle to a UI-owned view
  host; and the media-preview worker truncates its queue on the way out as every other worker does.

### Repository hygiene

`ui_text_view.h` (included by nothing), `pch.cpp` (compiled by no CMake target), eight
forward declarations of types that are never defined, and one enum value nothing produces are
removed. The workspace build tasks drove the solution file 1.27.2 deleted and now drive the CMake
build. The two copyright years a user actually sees — the shipped executable's version block and the
installer's — said 2024 and 2025 while every source header said 2026.

## Planned

### One date control, and it is ours

**Owned by [design](design.md).**

The Windows date picker is the only platform control left in the UI, ignores the app's scaling and theme, and has no Linux counterpart. [1.27.2 shipped the model](v-1.27.2.md#a-date-is-typed-rather-than-picked) and not the field, because building it turned up a blocker the plan did not know about: **a dialog does not give keyboard focus to anything it draws itself.** `dialog::key_down` returns false, and the one rendered control that receives keys — `search_control` — only does so because it owns a real platform edit window and forwards them through `capture_key_down`. Win32 tab order belongs to windows with `WS_TABSTOP`, so a drawn field cannot join it by being drawn.

Two ways out, and the choice is a decision this document owes before the code:

- **Element focus in the dialog host.** The dialog tracks a focused `view_element`, routes keys to it, and takes part in tab order through one hidden proxy window. It is the answer that removes the platform control, and it changes focus behaviour in every dialog.
- **A focus proxy per field.** The field keeps an invisible `WS_TABSTOP` child that owns focus and forwards keys, and every pixel is drawn by us. The scaling and theme complaints are answered and Linux supplies its own proxy, but a platform window remains.

A second piece is owed alongside it and is not a detail of the first: **nothing answers the display locale's field order.** `date_field_order` exists and the model reads it, but there is no platform query behind it, so "the order follows the display locale" is true of the test and of nothing else. It belongs beside `platform::environment` and may not reach a system header outside `platform*` files.

> **Start here.** [ui_date_edit.h](../src/ui_date_edit.h) is the model: segment order from the locale, digits left to right, stepping that rolls into the neighbour, and the day clamping a month or year step needs — all of it [shipped in 1.27.2](v-1.27.2.md#a-date-is-typed-rather-than-picked) and pinned by `Should edit a segmented date` in [test_view.cpp](../src/test_view.cpp). `date_time_control_impl` in [platform_win_ui.cpp](../src/platform_win_ui.cpp) is the `DATETIMEPICK_CLASS` wrapper being replaced, and `ui::date_control` in [ui_dialog.h](../src/ui_dialog.h) is its only caller. This is a `User-visible behavior` change.

### What the machine reports, beyond its identity

**Owned by [design](design.md).** Scope: all scopes — this is instrumentation, not behaviour.

[The packed platform identity shipped in 1.27.2](v-1.27.2.md#the-ping-says-what-the-machine-is). What it is designed to be sliced *by* is there; the things being measured are not. Each is a small daily histogram beside the key rather than a field inside it, so each answers one investment question outright and adding one later costs nothing and breaks no comparison:

| Counter | The investment it decides |
|---|---|
| AVX2 present | Whether the SSE2 baseline can rise and a dispatch path disappear |
| More than one display | Whether [#94](https://github.com/diffractor/diffractor/issues/94) multiple-monitor support has an audience |
| Touch input present | Whether [#37](https://github.com/diffractor/diffractor/issues/37) and [#38](https://github.com/diffractor/diffractor/issues/38) are worth building |
| Wide-gamut or HDR display | Whether colour management — a large deferred piece — would be seen by anyone |
| Collection includes a network, removable or cloud source | Whether the network and OneDrive cluster ([#8](https://github.com/diffractor/diffractor/issues/8), [#103](https://github.com/diffractor/diffractor/issues/103), [#196](https://github.com/diffractor/diffractor/issues/196)) is a niche or the common case |
| Collection size, as `log2(items)` | Where scale work pays, and the 32-bit memory ceiling. A log band never needs redefining, so old days stay comparable |
| Display language | Which of thirteen catalogs are worth maintaining |
| Linux distribution | Which packages to build, once there is something to package |
| Display scaling | Which of the "at each scaling" gates are worth the time |

**First run is a filter on the series, not a field in the key.** Counting first-run reports as their own daily series keyed on the same `s` answers *where new installs are arriving* — the sharpest investment signal there is — without doubling the table.

Anything open-ended stays out of the packed value entirely and travels as its own parameter carrying the real identifier — `l=de`, `d=ubuntu` — because there is no honest fixed width for a set that grows, and an "other" bucket destroys exactly the information worth having.

**One thing that would quietly cost data, and it is not a decision to take while implementing this.** `#ifndef WINSTORE` compiles the ping out entirely, so the Store population is invisible, and that skews the very number that would justify keeping Win32. It is recorded in [post-release context](v-next.md#1d-found-by-the-1272-pre-release-review) and needs an owner's answer, not an implementation decision.

> **Start here.** The ping is `check_for_updates_and_location` in [app.cpp](../src/app.cpp); `record_feature_use` and its neighbours in [app_settings.h](../src/app_settings.h) are the precedent for how a reported value is declared and commented. The remaining platform work is display capability, behind [platform.h](../src/platform.h) and implemented per platform beside `platform::environment`. Nothing may reach into a system header outside `platform*` files. This is an `Internal` change: it alters no observable behaviour, and the check that proves it is that the suite and the lint are unchanged.

### Linux support, stages 2 and 3

**Owned by [Linux port](linux.md).**

[Stage 0 and Stage 1](linux.md#staged-plan) are done: the platform boundary is provable, the
portable core passes its whole suite on a second toolchain, and the CPU rasterizer, its present
seam and the backend interface are portable. What stands between that and a usable picture is a
window and text — one deliverable, not two, because neither alone puts anything on screen.

The order is forced by a dependency the staging does not make obvious: **[Stage 3](linux.md#staged-plan)
comes before [Stage 2](linux.md#staged-plan)**, because DirectWrite is now the only thing holding
`software_draw_context` on Windows. Text first, then the window that presents it.

- **[Stage 3, text](linux.md#the-text-stack).** FreeType, HarfBuzz and fontconfig behind
  `measure_context` and `text_layout`, on Linux only — Windows keeps DirectWrite, recorded as
  [decision 9](linux.md#the-text-stack). New code rather than a refactor, and it carries the
  port's one genuine layout risk: two shapers mean two sets of advances, so a string can wrap
  differently on the two platforms.
- **[Stage 2, pixels](linux.md#staged-plan).** A window owning a BGRA buffer that satisfies
  `ui::software_present_target`. Its gate is already executable and green:
  `Should rasterise one scene to one answer on every platform` compares the two rasterizers today.

[Stage 4, input](linux.md#staged-plan) and beyond are out of scope and are listed in
[linux.md](linux.md#staged-plan).

One dependency is only half paid: 1.27.2 shipped the model that replaces the single platform date
picker, but not the field that draws it, so the date path still needs the work above before it has
a Linux equivalent.

Nothing in this stage changes Windows behaviour. If any of it does, it is a defect rather than a
feature.
