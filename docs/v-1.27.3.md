## Planned

### 1. Panorama display

**Owned by [zoom](zoom.md) and [design](design.md); the metadata it reads is owned by [metadata](metadata.md).**

An image carrying panorama metadata is not served by `Fit`: fitted to a browsing window a 12000x1000 stitch is a bright line. Zooming such an image should put the user inside it — 100% scale, the pointer looking around rather than dragging a scrollbar — instead of leaving them to pan a very wide rectangle by hand.

The intent, in the terms the [zoom model](zoom.md#2-the-model) already uses:

- Panorama display is **not a third magnified state**. Zoom's model is one scale and one source-space center, and a panorama is that model with the scale pinned to 100% and the center driven directly by the pointer. Introducing a state alongside `Fit`, inspect zoom and zoom mode would break [L8](zoom.md#3-the-laws) — no invisible modes — and is not the design.
- **Entry is the existing zoom entry.** Press-and-hold and `Ctrl+Space` remain the only ways in. What panorama metadata changes is what zoom mode *does* on entry for that image: it starts at 100% rather than the ladder's usual first stop, and the pointer looks around instead of requiring a drag.
- **Exit is the existing exit.** `Escape` peels one layer, per [L5](zoom.md#3-the-laws). Panorama display does not add a layer for `Escape` to peel.
- **The state is visible**, per [L6](zoom.md#3-the-laws). The navigator already shows where the visible region sits within the whole; a panorama is the case it exists for ([L10](zoom.md#3-the-laws)). The grading row and its vocabulary are unchanged.

Open decisions, each of which must be answered in [zoom](zoom.md) before code is written, since they change what the user can predict:

- **What qualifies as a panorama.** Nothing in `src/` reads the XMP `GPano` namespace today; the only current panorama signal is a genre string in [app_text.h](../src/app_text.h) and [model_index.cpp](../src/model_index.cpp), which is a keyword, not a projection. The candidates are the `GPano` properties written by phone panorama modes and stitchers, an aspect-ratio threshold, or both — and an aspect threshold alone will claim images that are merely wide.
- **Whether projection is honoured.** `GPano:ProjectionType` of `equirectangular` describes a sphere, not a flat strip. Reprojecting is a different renderer; drawing the strip flat at 100% is the [rendering tiers](zoom.md#4-rendering-tiers) that already exist. These are not the same feature and the release should claim only the one it ships.
- **What "look around using the mouse" means precisely.** Pointer position mapping to center is not drag-panning, and it interacts with [L1](zoom.md#3-the-laws) anchoring, with pointer capture, and with the [inspect zoom](zoom.md#21-two-magnified-states-one-zoom) press-and-hold gesture that is already bound to the same button.
- **Vertical behaviour.** A panorama taller than the viewport at 100% has a second axis; one shorter than it does not, and pinning it is the difference between looking around and jitter.

Constraints that are already settled and are not open:

- Detection reads metadata, so it is Source work. Nothing about it may run on the UI thread or inside a Paint function.
- [L11](zoom.md#3-the-laws) still binds: input responds within one frame from pixels already held, so a panorama that has not finished decoding looks around at reduced quality rather than stalling.
- [L12](zoom.md#3-the-laws) still binds: a provisional stand-in is marked as one.

### 2. One date vocabulary

**Owned by [design](design.md) for what the user sees, and [metadata](metadata.md) for which tag feeds it.**

Dates have produced more reports than any other subject — [#184](https://github.com/diffractor/diffractor/issues/184), [#192](https://github.com/diffractor/diffractor/issues/192) and the "click to open finds nothing" symptom in the same thread. 1.27.2 fixes the proximate defect. This is the structural answer, and it is a naming and precedence problem rather than a missing feature: the fields already exist.

What [model_property.h](../src/model_property.h) holds today, all three already `groupable | sortable`:

| Field | Search name | What it actually holds |
|---|---|---|
| `created_exif` | `created.exif` | EXIF `DateTimeOriginal` **and** XMP `photoshop:DateCreated` |
| `created_digitized` | `digitized` | EXIF `DateTimeDigitized`, XMP `xmp:CreateDate` |
| `created_utc` | **`created`** | the media container's own date |

Three things are wrong with how those are wired, and only the first is fixed in 1.27.2:

- **One field carries two concepts.** `DateTimeOriginal` is the shutter firing and no editor rewrites it; `photoshop:DateCreated` is nominally a mirror of it and is exactly what an editor does rewrite. 1.27.2 demotes the second below the first.
- **The user-facing names are inverted.** The property a user sees as "created" is the *container's* date; the capture time hides behind "created.exif". This reaches the search vocabulary too: in [model_property.cpp](../src/model_property.cpp), `taken`, `when`, `timeline` and `c` all resolve to `created_utc`, so `taken:2020` searches the container date rather than when the photo was taken.
- **Two precedence chains disagree.** `item_metadata::created()` resolves `created_exif` then `created_utc`; the timeline and heat-map path in [model_index.cpp](../src/model_index.cpp) resolves `created_exif`, `created_utc`, then `created_digitized`. A scanned photo can group under one date and appear on the timeline under another.

The intent is **fewer user-facing dates, not more**. A user does not know or care whether a capture time came from an EXIF tag or an MP4 header; they want to know when the picture was taken. That is one concept with a source ladder behind it, and one other concept beside it:

- **Taken** — the best available capture time, resolved by a single documented ladder, and what grouping, sorting and the timeline all use.
- **Modified** — `prop::modified`, unchanged.

`created.exif` and `digitized` stay as explicit fields, because sorting on the raw EXIF tag was an express request in [#184](https://github.com/diffractor/diffractor/issues/184) and is a legitimate thing to want. What changes is which one is the default and what the words mean.

Open decisions, each of which must be answered before code:

- **The exact ladder for Taken**, stated once in [metadata](metadata.md) and implemented once. The candidates in order are EXIF `DateTimeOriginal`, the container date, `photoshop:DateCreated`, then digitized — but the position of the container date relative to `photoshop:DateCreated` is a real question, and it differs between photographs and video.
- **What the words become.** "Date created" currently means the container date to the code and the capture date to the user. Renaming is user-visible, appears in group-by, sort-by, the properties panel and the search vocabulary, and touches all 13 translation catalogs.
- **What happens to a saved search.** Repointing `taken:` changes what an existing saved `taken:2019` returns. This is a fix rather than a regression, since the current behaviour is not what the word means, but it changes results silently and so belongs in the release notes rather than landing unannounced.

### 3. Linux support, stages 2 to 6

**Owned by [Linux port](linux.md).**

1.27.2 completed [Stage 0 and Stage 1](linux.md#staged-plan): the boundary is provable, the portable core passes its whole suite on a second toolchain, and the CPU rasterizer, its present seam and the backend interface are all portable. What is left before a Linux user can see anything is a window and text, and those two are a single deliverable rather than two — neither alone puts a usable picture on screen.

The order is forced by a dependency the staging does not make obvious: **[Stage 3](linux.md#staged-plan) comes before [Stage 2](linux.md#staged-plan)**, because DirectWrite is now the only thing holding `software_draw_context` on Windows. Text first, then the window that presents it.

- **[Stage 3, text](linux.md#the-text-stack).** FreeType, HarfBuzz and fontconfig behind `measure_context` and `text_layout`, on Linux only — Windows keeps DirectWrite, and [the reasoning](linux.md#the-text-stack) is recorded as decision 9. This is new code rather than a refactor, and it carries the port's one genuine layout risk: two shapers means two sets of advances, so a string can wrap differently on the two platforms.
- **[Stage 2, pixels](linux.md#staged-plan).** A window that owns a BGRA buffer and satisfies `ui::software_present_target`. Its gate is already executable and green — `Should rasterise one scene to one answer on every platform` compares the two platforms' rasterizers today.
- **[Stage 4, input](linux.md#staged-plan)** and beyond are not in scope for 1.27.3 and are listed in [linux.md](linux.md#staged-plan) rather than here.

Nothing in this subject changes Windows behaviour. If any of it does, it is a defect rather than a feature.
